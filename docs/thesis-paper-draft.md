# 基于个性化营养目标与协同过滤的健康食谱推荐系统设计与实现

## 摘要

随着居民健康意识提升和慢性病年轻化趋势加剧，饮食管理逐渐从单纯的经验判断转向以数据为基础的个性化决策。传统食谱平台通常以菜谱展示、分类检索和人工收藏为主，难以根据用户的身体数据、健康目标、饮食禁忌和实际摄入记录持续生成适配方案。针对这一问题，本文设计并实现了 NutriPlan 健康食谱推荐系统。系统采用前后端分离架构，前端基于 Vue 3、Vite、Element Plus 和 ECharts 构建交互界面，后端基于 Go、Gin、GORM 和 MySQL 实现用户管理、健康档案、营养目标计算、食谱推荐、饮食记录、营养统计、购物清单和后台管理等功能。

在推荐方法方面，系统首先根据用户性别、年龄、身高、体重和活动水平计算基础代谢率、每日总能量消耗与 BMI，再结合减脂、增肌、控糖和维持健康等目标确定目标热量和三大宏量营养素摄入量。在候选食谱阶段，系统按早餐、午餐、晚餐和加餐进行召回，并结合过敏源、饮食偏好、健康目标、适用人群、禁忌人群和近期饮食记录进行过滤。在个性化排序阶段，系统引入基于隐式反馈的 Item-CF 协同过滤方法，将收藏、已采纳计划和真实打卡记录聚合为用户-食谱偏好分，再计算食谱间相似度并生成候选加权分。最终系统通过规则约束与协同过滤融合的方式生成多套餐次组合，并根据营养匹配度、跨餐重复和食材多样性进行评分排序。测试结果表明，系统能够完成用户健康档案维护、每日食谱推荐、饮食记录统计和后台管理等核心流程，并能在冷启动和行为数据不足时回退到规则推荐策略，具有较好的实用性和扩展性。

关键词：健康饮食；食谱推荐；个性化推荐；Item-CF；营养目标；前后端分离

## 第1章 绪论

### 1.1 课题研究背景及意义

膳食结构与居民健康状况密切相关。世界卫生组织指出，健康饮食有助于预防营养不良以及糖尿病、心血管疾病、卒中和癌症等非传染性疾病，并建议成年人摄入充足蔬果、限制游离糖、饱和脂肪和反式脂肪摄入[1]。在国内，《中国居民膳食指南（2022）》提出食物多样、合理搭配、吃动平衡、规律进餐、足量饮水等原则，为居民日常膳食提供了基础参考[2]。然而，在真实生活场景中，用户通常难以长期、准确地将这些原则转化为每日餐单：一方面，用户的性别、年龄、身高、体重、活动水平和健康目标不同，对热量和宏量营养素的需求存在差异；另一方面，用户还可能存在过敏源、饮食偏好、控糖需求、减脂需求或增肌需求，通用菜谱难以满足个体化饮食管理要求。

推荐系统为解决信息过载和个性化选择问题提供了有效手段。协同过滤、内容推荐和混合推荐等方法已广泛应用于电子商务、新闻、音乐和视频平台。与一般内容推荐不同，健康饮食推荐既要考虑用户偏好，也必须满足营养目标和安全约束。因此，单纯根据点击、收藏或相似用户行为进行推荐并不充分，推荐结果还应受到热量、蛋白质、碳水化合物、脂肪、餐次类型、过敏源和近期重复饮食等因素约束。

本课题的研究意义主要体现在三方面。第一，在应用层面，系统能够帮助用户根据个人健康档案自动生成早餐、午餐、晚餐和加餐方案，降低日常饮食规划成本。第二，在方法层面，系统将营养规则约束与 Item-CF 协同过滤结合，在保证健康约束优先的基础上引入用户行为偏好。第三，在工程层面，系统实现了从健康档案录入、推荐方案生成、计划采纳、饮食打卡、统计反馈到购物清单生成的闭环，为后续扩展智能膳食管理和健康行为分析提供基础。

### 1.2 国内外研究现状

#### 1.2.1 推荐系统研究现状

推荐系统主要用于根据用户历史行为、物品属性和上下文信息预测用户可能感兴趣的内容。早期推荐系统常采用基于内容的推荐和协同过滤方法。基于内容的推荐依赖物品自身特征，如食谱中的食材、餐次、口味、营养成分和健康标签；协同过滤则从群体行为中学习相似用户或相似物品之间的关联。Sarwar 等提出的基于物品的协同过滤算法通过计算物品之间的相似度进行推荐，在电商推荐场景中具有较好的可解释性和可扩展性[3]。Koren 等总结的矩阵分解方法进一步提升了稀疏评分矩阵中的隐含特征学习能力，并成为推荐系统研究的重要方向[4]。

近年来，推荐系统逐渐从单一算法转向混合推荐和约束推荐。Burke 对混合推荐系统进行了系统性总结，指出不同推荐策略可以通过加权、切换、级联、特征融合等方式组合，以弥补单一方法的局限[5]。在健康食谱推荐场景下，混合推荐尤其重要，因为用户偏好只是推荐依据之一，系统还必须考虑营养均衡、健康风险和饮食禁忌。因此，本文采用“规则约束优先、协同过滤加权”的混合策略：协同过滤用于从用户行为中获得偏好信号，营养与禁忌规则用于保证推荐结果不会偏离健康目标。

#### 1.2.2 健康饮食推荐研究现状

健康饮食推荐与传统推荐系统相比具有更强的约束性和专业性。普通推荐场景通常关注点击率、转化率或用户满意度，而健康饮食推荐还需要考虑能量摄入、营养素比例、餐次分配、饮食禁忌和慢病风险。Mifflin-St Jeor 方程是估算静息能量消耗的经典方法之一，常用于根据性别、年龄、身高和体重估算基础代谢水平[6]。在此基础上，结合活动系数可以得到每日总能量消耗，为个性化热量目标提供依据。

国内外健康饮食推荐系统通常包含三个关键环节：用户健康画像建模、食物或食谱营养信息建模、推荐生成与反馈。用户画像包括年龄、性别、身体指标、健康目标、过敏源和偏好；食谱画像包括餐次类型、食材、烹饪方式、热量和营养素；推荐模型则需要在用户偏好与营养约束之间进行平衡。本文系统在实现上以用户健康档案为输入，使用营养目标计算模块确定每日热量和宏量营养素目标，再在推荐模块中按照餐次生成组合方案，最后通过饮食记录和收藏行为形成反馈闭环。

### 1.3 研究内容

本文围绕健康食谱推荐系统的设计与实现展开，主要研究内容如下。

第一，设计用户健康档案模型。系统记录用户账号、角色、性别、年龄、身高、体重、活动水平、每日进食次数、健康目标、目标体重、BMI、BMR、TDEE、饮食调节模式、过敏源、饮食偏好和健康状况等信息，为后续营养计算和推荐过滤提供基础。

第二，设计个性化营养目标计算方法。系统根据用户身体数据计算 BMR、BMI 和 TDEE，并依据健康目标对 TDEE 进行调整，得到目标热量；随后按照不同健康目标分配蛋白质、碳水化合物和脂肪比例。

第三，设计融合规则约束与协同过滤的推荐方法。系统基于餐次类型召回候选食谱，结合过敏源、健康目标、饮食偏好和近期历史进行过滤；同时利用收藏、采纳计划和打卡记录构造隐式反馈，通过 Item-CF 计算相似食谱候选，并将协同过滤分数作为候选排序加成。

第四，实现完整健康饮食管理系统。系统包括普通用户功能和管理员功能。普通用户可完成注册登录、健康档案维护、食谱推荐、推荐方案选择、饮食记录、营养统计、食谱收藏和购物清单生成；管理员可管理食谱数据并查看健康统计和食谱完成情况。

第五，开展系统测试与结果分析。通过功能测试、推荐效果测试和性能测试验证系统核心功能是否符合需求，分析推荐结果在营养匹配度、多样性和可用性方面的表现。

### 1.4 论文组织结构

全文共分为六章。第1章介绍课题背景、研究意义、国内外研究现状和研究内容。第2章分析系统设计目标、功能需求和非功能需求。第3章阐述系统总体架构、功能模块、业务流程、数据库总体设计以及开发方案选择。第4章重点介绍个性化食谱推荐方法，包括营养目标计算、候选召回与过滤、协同过滤建模、规则融合和方案评分。第5章说明系统数据库、后端功能和前端页面的具体实现。第6章进行系统测试与结果分析。最后对全文工作进行总结，并展望后续优化方向。

## 第2章 系统需求分析

### 2.1 系统设计目标

NutriPlan 系统的总体目标是构建一个面向普通用户的个性化健康食谱推荐平台。系统应能够根据用户健康档案自动计算营养需求，生成符合用户目标和禁忌要求的每日食谱方案，并支持用户对实际饮食进行记录和统计。系统还应提供后台管理能力，便于管理员维护食谱数据、查看用户健康状态和分析推荐完成情况。

具体目标包括：一是个性化，推荐结果应体现用户身体指标、健康目标、饮食偏好和行为反馈差异；二是安全性，食谱不得违反用户过敏源和禁忌人群约束；三是营养合理性，推荐方案应尽量贴近目标热量和三大营养素需求；四是可用性，系统应提供清晰、易操作的前端页面，降低用户记录和选择成本；五是可扩展性，推荐算法和业务模块应采用分层设计，便于后续接入更多行为数据、AI 识别能力或更复杂的推荐模型。

### 2.2 功能需求分析

#### 2.2.1 普通用户功能需求

普通用户功能需求包括以下方面。

1. 注册与登录。用户可通过用户名、密码和邮箱完成账号注册，并通过登录获取 JWT 令牌。系统后续接口通过认证中间件识别用户身份。

2. 健康档案维护。用户可维护性别、年龄、身高、体重、活动水平、健康目标、过敏源、饮食偏好、健康状况和每日进食次数等信息。系统在档案更新时计算 BMR、TDEE 和 BMI，并保存结果。

3. 营养需求查看。用户可查看当前每日目标热量、目标蛋白质、目标碳水化合物和目标脂肪。该功能帮助用户理解推荐方案的依据。

4. 食谱推荐。用户可请求每日推荐方案。每套方案包含早餐、午餐、晚餐和加餐，并展示总热量、三大营养素和匹配度评分。系统支持生成多套方案供用户选择。

5. 推荐计划选择与替换。用户可采纳某套推荐计划，也可针对单餐进行替换或受限重构，以适应已有食材或临时口味变化。

6. 食谱详情与收藏。用户可查看食谱名称、图片、餐次类型、食材、烹饪步骤、推荐食用量、热量和宏量营养素，并可收藏或取消收藏食谱。

7. 饮食记录与统计。用户可手动添加饮食记录，也可通过图片识别或文本分析辅助记录。系统按日统计热量、蛋白质、碳水化合物和脂肪摄入，并提供周报统计。

8. 购物清单。用户可根据已选食谱生成购物清单，并对清单进行查看、编辑、完成和删除。

#### 2.2.2 管理员功能需求

管理员功能主要用于维护系统基础数据和观察系统运行效果。管理员通过角色权限控制访问后台接口，可执行食谱列表查询、食谱详情查看、食谱新增、修改、删除等操作。同时，管理员可查看用户健康统计和食谱完成统计，为优化食谱库和推荐策略提供依据。

### 2.3 非功能需求分析

1. 安全性。系统应对密码进行加密存储，认证接口使用 JWT，管理员接口必须进行角色校验。涉及用户健康档案和饮食记录的数据应避免在非授权场景下泄露。

2. 可维护性。系统后端采用 handler、service、dao 和 model 分层结构，前端采用 api、views、components、store 和 router 分层组织，便于定位问题和迭代功能。

3. 可靠性。推荐算法应具备冷启动和兜底能力。当协同过滤无候选、候选过滤后为空或某餐次组合不足时，系统应回退到规则推荐或放宽部分非安全约束，避免返回空结果。

4. 性能。推荐过程中存在候选召回、组合生成和全日方案评分，系统应通过候选截断、热量剪枝、缓存和多样性过滤控制计算量。当前 Item-CF 使用 90 天行为窗口，并提供短 TTL 内存缓存，减少同一用户多餐次重复计算。

5. 易用性。前端应提供清晰的健康档案页、推荐页、饮食记录页和统计页，减少复杂表单和重复输入，帮助用户快速完成推荐选择和打卡。

### 2.4 本章小结

本章从系统目标、普通用户需求、管理员需求和非功能需求四个方面进行了分析。需求分析表明，系统不只是食谱展示平台，而是围绕健康档案、个性化推荐、饮食记录和统计反馈构建的闭环应用。后续章节将在此基础上进行总体设计和具体实现。

## 第3章 系统总体方案设计

### 3.1 系统总体架构设计

系统采用前后端分离架构。前端基于 Vue 3 和 Vite 构建单页应用，通过 Axios 与后端 RESTful API 通信；后端基于 Go 和 Gin 实现 HTTP 服务，通过 GORM 访问 MySQL 数据库；数据库保存用户、食谱、每日推荐计划、饮食记录、收藏、购物清单等数据。系统整体可分为表现层、接口层、业务逻辑层、数据访问层和数据存储层。

表现层由 Vue 页面和组件组成，包括登录注册、首页、健康档案、食谱推荐、食谱详情、饮食记录、周报、购物清单、收藏列表和管理员页面。接口层由 Gin router 和 handler 组成，负责路由分组、参数绑定、身份认证和响应封装。业务逻辑层由 user service、nutri service、recipe service、intake service、shopping list service、admin service 和 food recognition service 组成。数据访问层由 repository/dao 负责封装数据库查询。数据存储层使用 MySQL，模型结构通过 GORM 定义。

### 3.2 系统功能模块设计

#### 3.2.1 用户与健康档案模块

用户与健康档案模块负责账号注册、登录认证、健康档案更新、营养需求查询和饮食模式管理。用户模型包括账号信息、身体数据、健康目标、饮食模式和标签类数据。用户更新档案后，系统调用营养计算服务，根据身高、体重、年龄、性别和活动水平计算 BMR、TDEE 和 BMI，并将结果保存至用户表。

#### 3.2.2 食谱推荐模块

食谱推荐模块是系统核心模块。该模块以用户健康档案为输入，先计算每日目标热量和宏量营养素，再按餐次召回候选食谱。候选食谱经过允许餐次、过敏源、适用人群、禁忌人群、健康目标、饮食模式和近期历史过滤后，进入单餐组合生成阶段。系统分别为早餐、午餐、晚餐和加餐生成候选组合，并通过全日方案评分选择多套推荐结果。若用户存在足够行为数据，系统还会调用 Item-CF 生成协同过滤候选，并将其作为排序加成参与推荐。

#### 3.2.3 饮食记录与营养统计模块

饮食记录模块用于记录用户实际摄入。记录字段包括用户 ID、记录日期、餐次类型、食物来源、来源 ID、食物名称、摄入量、实际热量、实际蛋白质、实际碳水化合物和实际脂肪。系统可按日汇总当前摄入，并与目标值比较，计算达标率；也可按周生成统计报告。真实打卡记录还会作为协同过滤中的强正反馈，推动推荐结果随着用户行为动态调整。

#### 3.2.4 辅助功能与后台管理模块

辅助功能包括食谱收藏、购物清单和 AI 食物识别。收藏行为可作为用户偏好信号；购物清单用于将已选食谱转换为采购任务；AI 食物识别和文本分析用于辅助用户记录实际饮食。后台管理模块提供食谱数据维护、健康统计和食谱完成情况统计，管理员接口由 JWT 认证和角色校验共同保护。

### 3.3 系统业务流程设计

#### 3.3.1 食谱推荐业务流程

食谱推荐流程如下：用户登录后提交或更新健康档案；系统计算 BMR、TDEE、BMI、目标热量和宏量营养素；推荐服务按早餐、午餐、晚餐和加餐召回候选食谱；候选食谱经过规则过滤和近期重复过滤；协同过滤模块根据用户历史行为返回候选食谱及分数；系统合并规则候选和协同过滤候选，生成单餐组合；全日方案生成器对早餐、午餐、晚餐和加餐组合进行组合、剪枝、评分和排序；系统返回多套推荐计划；用户选择其中一套，计划被标记为已采纳，并可进一步生成饮食记录或购物清单。

#### 3.3.2 饮食记录业务流程

饮食记录流程如下：用户进入饮食记录页面，选择手动录入、图片识别或文本分析方式添加记录；系统保存记录日期、餐次、食物来源、摄入量和营养素计算结果；当用户查看当日营养状态时，系统汇总当日所有记录，并与用户营养目标比较；当用户查看周报时，系统按日期聚合多日记录并生成平均摄入、总摄入和达标情况。若记录来自系统食谱，记录中的 source_id 将作为协同过滤反馈数据。

### 3.4 数据库总体设计

数据库围绕用户、食谱、计划、记录和辅助功能展开。核心表包括 users、recipes、daily_recipe_plans、daily_intake_records、user_favorite_recipes 和 shopping_lists。users 表保存用户健康档案和营养计算结果；recipes 表保存食谱基础信息、餐次、营养信息、食材、步骤和健康标签；daily_recipe_plans 表保存推荐计划、餐次食谱 ID、组合明细、计划营养值、目标营养值和匹配度；daily_intake_records 表保存真实饮食打卡记录；user_favorite_recipes 表保存收藏关系；shopping_lists 表保存购物清单内容和状态。

### 3.5 系统开发方案分析与选择

#### 3.5.1 架构模式分析与选择

本系统选择前后端分离架构。该架构将界面交互和业务服务解耦，前端负责页面渲染和用户体验，后端负责数据处理、认证授权和推荐计算。相比服务端模板渲染，前后端分离更适合包含多页面交互、图表统计、推荐方案切换和打卡反馈的应用。同时，RESTful API 也便于后续扩展移动端或第三方服务。

#### 3.5.2 开发框架分析与选择

前端选择 Vue 3 和 Vite。Vue 3 提供组件化开发能力，适合构建健康档案表单、推荐卡片、统计面板等复用组件；Vite 提供快速开发服务和构建能力[7]。前端还使用 Element Plus、Naive UI、Pinia、Vue Router、Axios 和 ECharts，分别承担 UI 组件、状态管理、路由、接口请求和数据可视化。后端选择 Go 和 Gin，Gin 是 Go 生态中常用的 Web 框架，适合构建高性能 REST API[8]。数据库访问使用 GORM，能够通过模型结构映射 MySQL 表，并支持关联查询、软删除和 JSON 序列化字段[9]。认证采用 JWT，符合 RFC 7519 中 JSON Web Token 的令牌化身份传递方式[10]。

### 3.6 本章小结

本章给出了系统总体架构、功能模块、业务流程、数据库总体设计和开发方案选择。系统采用前后端分离和后端分层设计，为推荐算法、饮食记录和后台管理提供了清晰的工程结构。

## 第4章 个性化食谱推荐方法的设计与实现

### 4.1 用户营养目标计算

#### 4.1.1 用户健康数据建模

用户健康数据模型主要包括性别、年龄、身高、体重、活动水平、健康目标、目标体重、过敏源、饮食偏好和健康状况。系统还保存 BMR、TDEE 和 BMI 等计算结果。BMI 的计算公式为：

```text
BMI = weight / (height / 100)^2
```

其中 weight 单位为 kg，height 单位为 cm。

#### 4.1.2 目标热量计算

系统采用 Mifflin-St Jeor 思路计算基础代谢率。实现中先计算基础项：

```text
baseBMR = 10 * weight + 6.25 * height - 5 * age
```

当用户为男性时：

```text
BMR = baseBMR + 5
```

当用户为女性时：

```text
BMR = baseBMR - 161
```

随后根据活动水平乘以活动系数得到 TDEE：

```text
TDEE = BMR * activityFactor
```

活动系数包括久坐 1.2、轻度活动 1.375、中度活动 1.55、重度活动 1.725、极重度活动 1.9。目标热量根据健康目标调整：

```text
targetCalorie = TDEE + goalAdjustment
```

其中，减脂目标采用热量赤字，增肌目标采用热量盈余，控糖目标采用轻微热量赤字，维持健康目标保持 TDEE 不变。系统还设置最低安全热量，避免目标热量过低。

#### 4.1.3 宏量营养素与餐次比例分配

系统根据健康目标分配蛋白质、碳水化合物和脂肪比例。当前实现中，减脂目标采用 25% 蛋白质、40% 碳水、35% 脂肪；增肌目标采用 30% 蛋白质、50% 碳水、20% 脂肪；控糖目标采用 25% 蛋白质、35% 碳水、40% 脂肪；维持健康目标采用 20% 蛋白质、55% 碳水、25% 脂肪。营养素克数按照蛋白质和碳水每克 4 kcal、脂肪每克 9 kcal 进行换算：

```text
proteinGram = targetCalorie * proteinRatio / 4
carbGram = targetCalorie * carbRatio / 4
fatGram = targetCalorie * fatRatio / 9
```

在餐次分配方面，系统将每日目标按照早餐 25%、午餐 35%、晚餐 30%、加餐 10% 拆分，使单餐组合生成能够围绕局部目标进行评分。

### 4.2 候选食谱召回与过滤

#### 4.2.1 基于餐次类型的候选召回

系统以餐次为基本召回单位，分别构建早餐、午餐、晚餐和加餐候选池。召回时综合考虑餐次类型、目标热量、健康目标、用户标签和禁用食材。当前系统支持传统热量接近召回、低热量召回、高热量召回、偏好标签召回和随机探索召回。多路召回能够避免候选来源单一，提高推荐结果的覆盖率和多样性。

#### 4.2.2 基于健康目标与饮食禁忌的过滤

召回后的食谱必须经过规则过滤。首先，系统根据 allowed_meal_types 判断食谱是否支持当前餐次；其次，根据用户过敏源和禁忌食材排除不安全食谱；再次，根据食谱的 target_users 和 forbidden_users 判断其是否适合用户健康目标、饮食偏好和健康状况；最后，根据健康目标使用 is_weight_loss_friendly、is_muscle_gain_friendly、is_sugar_control_friendly 和 is_general_friendly 等标签进行过滤。该阶段将健康安全作为硬约束，避免协同过滤分数绕过禁忌规则。

#### 4.2.3 基于近期记录的重复食谱过滤

为了避免用户短期内重复摄入相同食谱，系统会查询近期计划和饮食记录，对最近出现过的食谱进行过滤或降权。重复过滤可提升用户体验，也能促进食材和营养来源多样化。当候选池过小导致推荐无法生成时，系统会逐级放宽近期重复等非安全约束，保证推荐接口可用。

### 4.3 个性化推荐策略设计

#### 4.3.1 用户行为偏好建模

系统使用隐式反馈构建用户-食谱偏好。行为来源包括收藏食谱、已采纳推荐计划和真实饮食打卡记录。三类行为权重不同：收藏权重为 2.0，采纳计划权重为 3.0，真实打卡权重为 5.0。真实打卡代表用户实际执行行为，因此权重最高。偏好分还引入时间衰减：

```text
preference(u, i) = sum(weight(e) * exp(-daysAgo(e) / 30))
```

其中 u 表示用户，i 表示食谱，e 表示用户对食谱产生的行为事件。时间衰减使近期行为对推荐结果产生更大影响。

#### 4.3.2 基于 Item-CF 的协同过滤推荐

Item-CF 的核心思想是根据用户群体行为计算食谱之间的相似度，再根据当前用户历史偏好预测其可能喜欢的未见食谱。系统首先构造食谱-用户偏好向量：

```text
V_i = {u1: score(u1,i), u2: score(u2,i), ...}
```

然后使用余弦相似度计算两个食谱之间的相似度：

```text
sim(i, j) = dot(V_i, V_j) / (||V_i|| * ||V_j||)
```

对于目标用户 u，候选食谱 j 的协同过滤分数为：

```text
cf_score(u, j) = sum(preference(u, i) * sim(i, j)) / sum(abs(sim(i, j)))
```

其中 i 是用户已有历史行为食谱。系统过滤掉用户已经产生行为的食谱，只对未见候选进行排序。若用户没有行为历史，Item-CF 返回空结果，系统自动使用规则推荐兜底。

#### 4.3.3 规则约束与协同过滤融合

系统采用轻量融合策略：协同过滤不直接决定最终方案，而是为候选食谱提供排序加成。具体流程为：Item-CF 先按餐次返回候选食谱及分数；系统将协同过滤候选与规则召回候选按食谱 ID 合并去重；协同过滤分数归一化后作为 scoreBoosts 注入候选排序；随后所有候选仍需经过健康目标、饮食模式、过敏禁忌、近期历史、单餐组合评分和全日方案评分。该设计保证了推荐结果既能体现用户偏好，又不会突破营养和安全约束。

### 4.4 食谱方案生成与评分

#### 4.4.1 单餐组合生成规则

系统不是简单地为每餐推荐一道菜，而是生成单餐多食物组合。早餐支持 1 至 2 道食谱组合，并对“酸奶 + 鸡蛋”等稳定早餐搭配给予优先权。午餐和晚餐支持 1 至 3 道食谱组合，并要求优先包含主食，避免餐单结构不完整。加餐支持 0 至 2 道食谱组合，当加餐候选不足时允许空加餐兜底。每个组合都会计算总热量、蛋白质、碳水化合物和脂肪，并根据单餐目标进行局部评分。

#### 4.4.2 餐次数量与主食约束设计

早餐、午餐、晚餐和加餐具有不同的饮食结构。早餐通常强调便捷性和稳定性，因此组合数量较少；午餐和晚餐承担主要能量摄入，组合数量较多，并通过主食约束保证碳水来源；加餐作为补充餐次，主要用于平衡全天热量或蛋白质缺口。餐次数量和主食约束使推荐结果更接近真实饮食场景。

#### 4.4.3 全日方案评分与排序

系统将早餐组合、午餐组合、晚餐组合和加餐组合进行笛卡尔积组合，并在组合过程中进行剪枝。若当前组合热量超过目标热量的 1.3 倍，则直接跳过；若跨餐出现重复食谱，也直接跳过。对于可行方案，系统计算全日总热量、总蛋白质、总碳水化合物和总脂肪，并与目标值比较。综合评分采用带权相对偏差：

```text
diff = wE * |E - Et| / Et
     + wP * |P - Pt| / Pt
     + wC * |C - Ct| / Ct
     + wF * |F - Ft| / Ft
```

其中 E、P、C、F 分别表示方案热量、蛋白质、碳水和脂肪，Et、Pt、Ct、Ft 表示目标值。不同健康目标对应不同权重：增肌更重视能量和蛋白质，减脂更重视能量和脂肪控制，控糖更重视能量和碳水控制，维持健康采用较均衡的权重。最终匹配度分数可映射到 0 至 100 分，偏差越小分数越高。

#### 4.4.4 多样性控制与替换策略

多样性控制包括三类规则。第一，跨餐食谱不得重复出现。第二，系统对跨餐食材重叠进行惩罚，鼓励全天食材来源更加丰富。第三，最终结果会进行多样性过滤，避免多套推荐计划高度相似。在用户已有食材受限的情况下，系统支持单餐重构和采纳重构结果。单餐重构会在已有计划的基础上保留其他餐次，仅针对目标餐次重新生成组合，并重新计算全日营养和匹配度。

### 4.5 本章小结

本章介绍了系统推荐算法的设计与实现。算法以营养目标计算为基础，以规则过滤保证健康安全，以 Item-CF 引入行为偏好，以单餐组合和全日评分生成最终方案。该方法兼顾了营养合理性、个性化和工程可落地性。

## 第5章 系统设计与实现

### 5.1 系统开发环境与技术栈

系统后端使用 Go 1.24，主要依赖 Gin、GORM、MySQL driver、Viper、JWT 和 bcrypt。前端使用 Vue 3、Vite、Vue Router、Pinia、Axios、Element Plus、Naive UI、ECharts、html2canvas 和 jsPDF。数据库使用 MySQL。开发过程中，后端通过 `go test ./...` 进行单元测试，前端通过 `npm run build` 或 `npx vite build` 进行构建验证。

### 5.2 数据库详细设计

#### 5.2.1 用户信息表设计

users 表用于保存用户账号和健康档案。主要字段包括 id、username、password、email、role、gender、age、height、weight、activity_level、meal_times_per_day、last_profile_update、health_goal、target_weight、bmi、tdee、bmr、diet_mode、diet_mode_source、diet_mode_reason、diet_mode_until、allergies、dietary_prefs 和 health_conditions。username 设置唯一索引，role 设置索引，密码字段不返回给前端。

#### 5.2.2 食谱信息表设计

recipes 表用于保存食谱基础数据。主要字段包括 id、name、image_url、meal_type、allowed_meal_types、difficulty、cooking_time、portion_weight_g、energy、protein、carbohydrate、fat、ingredients、cooking_steps、target_users、forbidden_users、is_weight_loss_friendly、is_muscle_gain_friendly、is_sugar_control_friendly 和 is_general_friendly。allowed_meal_types、ingredients、cooking_steps、target_users 和 forbidden_users 使用 JSON 序列化字段，便于保存列表型信息。

#### 5.2.3 每日食谱计划表设计

daily_recipe_plans 表用于保存系统生成的每日推荐计划。主要字段包括 user_id、plan_date、plan_name、is_selected、breakfast_recipe_id、lunch_recipe_id、dinner_recipe_id、snack_recipe_id、breakfast_item_ids、lunch_item_ids、dinner_item_ids、snack_item_ids、total_energy、total_protein、total_carbohydrate、total_fat、target_energy、target_protein、target_carbohydrate、target_fat 和 match_score。单餐主食谱 ID 用于兼容旧接口，item_ids 用于保存多食物组合。

#### 5.2.4 饮食记录表设计

daily_intake_records 表用于保存用户真实饮食记录。主要字段包括 user_id、record_date、meal_type、food_source、source_id、food_name、intake_amount、calculated_energy、calculated_protein、calculated_carb 和 calculated_fat。其中 food_source 用于区分记录来自系统食谱还是基础食物，source_id 用于关联对应来源。该表既服务于营养统计，也为协同过滤提供真实打卡反馈。

### 5.3 后端功能设计与实现

#### 5.3.1 用户与健康档案功能实现

后端通过 user handler 接收注册、登录、档案更新和营养需求查询请求。注册时系统校验用户名唯一性并加密密码；登录成功后生成 JWT。档案更新时，user service 调用 nutri service 计算 BMR、TDEE 和 BMI，并保存至 users 表。

#### 5.3.2 营养需求计算功能实现

营养需求计算由 nutri service 实现。该服务包含 CalculateTDEE、DetermineTargetCalorie、AllocateMacros 和 CalculateNutritionTargets 等方法，分别负责身体指标计算、目标热量计算、宏量营养素分配和完整营养目标返回。

#### 5.3.3 食谱推荐功能实现

食谱推荐由 recipe service 和 recommendation 相关模块实现。RecipeServiceImpl 持有 recipe repository、daily plan repository、nutri service、behavior repository 和 collaborative filter。推荐入口先计算营养目标和饮食模式，再构建规则候选池和协同过滤候选池。协同过滤候选通过 normalizeCollaborativeScoreBoosts 转化为加权分，参与候选排序。最终 generateRankedPlans 负责生成单餐组合、全日组合、营养评分、多样性惩罚和排序。

#### 5.3.4 饮食记录与营养统计功能实现

intake service 负责新增记录、删除记录、当日营养状态统计和周报统计。新增记录时，系统保存实际摄入量和计算后的营养值；统计时，系统按日期和餐次聚合记录，并返回目标值、实际值和达标率。记录来自系统推荐食谱时，可通过 food_source 和 source_id 参与用户行为建模。

#### 5.3.5 购物清单与后台管理功能实现

shopping list service 根据食谱 ID 和食材信息生成购物清单，支持列表查询、详情查看、编辑、删除和完成状态更新。admin service 提供后台食谱管理、健康统计和完成率统计。管理员路由使用 JWT 中间件和角色中间件共同保护，只有管理员角色可访问。

### 5.4 前端功能设计与实现

#### 5.4.1 登录注册与健康档案页面实现

前端通过 Login.vue 和 Register.vue 实现登录注册流程，通过 Pinia 保存认证状态，通过 Axios 请求拦截器携带 JWT。Profile.vue 和 ProfileView.vue 实现健康档案录入和展示，用户可维护身体数据、活动水平、健康目标、过敏源和饮食偏好。

#### 5.4.2 食谱推荐页面实现

RecipeRecommend.vue 调用推荐接口获取多套每日方案，并展示早餐、午餐、晚餐和加餐组合。页面展示每套方案的热量、蛋白质、碳水、脂肪和匹配度，并支持方案选择、单餐替换、受限重构和采纳重构。RecipeCard、MealItem 和 RecipeImage 等组件用于复用食谱展示逻辑。

#### 5.4.3 饮食记录与统计页面实现

IntakeRecord.vue 实现饮食记录添加、删除和当日统计展示。WeeklyReport.vue 用于展示周期性营养统计。ECharts 用于绘制摄入趋势和营养结构图，使用户能够直观看到实际摄入与目标之间的差距。

#### 5.4.4 购物清单与后台管理页面实现

ShoppingList.vue 实现购物清单创建、查看、编辑和完成。AdminHome.vue 提供后台管理入口，配合后端 admin API 完成食谱管理和统计查看。前端路由通过权限信息控制页面访问，未授权用户会跳转到登录或 forbidden 页面。

### 5.5 本章小结

本章从技术栈、数据库设计、后端实现和前端实现四个方面描述了系统落地过程。系统通过分层后端结构和组件化前端结构实现了完整健康饮食推荐闭环。

## 第6章 系统测试与结果分析

### 6.1 测试环境与测试方法

系统测试可分为单元测试、功能测试、推荐效果测试和性能测试。单元测试主要验证营养计算、行为聚合、Item-CF 相似度计算、冷启动回退、单餐组合生成和多样性惩罚。功能测试通过接口和前端页面验证注册登录、档案更新、推荐生成、方案选择、饮食记录、周报统计、购物清单和后台管理。推荐效果测试关注推荐方案是否满足营养目标、是否避开过敏禁忌、是否减少近期重复、是否体现协同过滤偏好。性能测试关注推荐接口响应时间和候选组合数量。

### 6.2 功能测试及结果分析

功能测试可按照模块设计测试用例。用户模块测试注册、登录、档案更新和营养需求查询。食谱推荐模块测试无行为用户和有行为用户两种场景，验证系统均能返回推荐计划。饮食记录模块测试新增、删除、当日统计和周报统计。购物清单模块测试创建、查询、更新、删除和完成。后台模块测试管理员权限控制和食谱维护。根据当前代码结构，系统已提供 recipe service、recommendation behavior、recommendation collaborative filter 和 handler 等测试文件，说明核心推荐逻辑具备单元测试基础。

### 6.3 推荐效果测试与分析

推荐效果测试可从三方面进行。第一，营养匹配度：检查推荐方案总热量和宏量营养素是否接近用户目标，并记录 match_score。第二，约束符合度：检查推荐结果是否包含用户过敏源、禁忌人群或不适合健康目标的食谱。第三，个性化程度：为用户构造收藏、采纳计划和真实打卡记录，验证协同过滤候选是否参与推荐排序，并观察与历史偏好相似的食谱是否更容易进入候选池。系统设计中，协同过滤只是加权信号，最终仍受营养和禁忌规则控制，因此推荐结果更适合健康场景。

### 6.4 性能测试及结果分析

推荐接口性能主要受候选数量、组合生成规模和协同过滤计算影响。系统通过餐次候选截断、组合数量限制、热量上限剪枝、重复过滤和 Item-CF 短 TTL 缓存降低计算量。测试时可分别记录无协同过滤、有协同过滤缓存未命中、有协同过滤缓存命中三种情况下的响应时间。若后续食谱和行为数据规模扩大，可进一步将 Item-CF 相似度离线预计算并保存至 recipe_similarities 表，以降低在线计算压力。

### 6.5 本章小结

本章提出了系统测试方案和结果分析维度。测试重点不仅包括功能是否可用，还包括推荐结果是否符合健康约束、是否具有个性化特征以及推荐接口是否满足实际使用性能要求。

## 总结与展望

本文设计并实现了一个基于个性化营养目标与协同过滤的健康食谱推荐系统。系统围绕用户健康档案、营养目标计算、食谱推荐、饮食记录、营养统计、购物清单和后台管理构建完整闭环。在推荐方法上，系统结合 Mifflin-St Jeor 能量估算、健康目标热量调整、宏量营养素分配、餐次组合生成、规则过滤、Item-CF 协同过滤和多样性评分，实现了兼顾健康约束和用户偏好的混合推荐。

系统仍有进一步优化空间。第一，可引入更完整的食物营养数据库，提升食谱营养数据准确性。第二，可将用户行为统一写入事件表，支持更细粒度的浏览、点击、替换、拒绝和完成反馈。第三，可将 Item-CF 相似度改为离线预计算或定时更新，提高大规模数据下的性能。第四，可引入 A/B 测试和推荐日志，量化不同推荐策略对用户采纳率、完成率和营养达标率的影响。第五，可结合可解释推荐，在前端展示“为何推荐该食谱”，增强用户对推荐结果的信任。
